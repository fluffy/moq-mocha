--- abstract

This document specifies how MOCHA users establish peer-to-peer
trust through a cryptographic key binding chain. Each user has
a long-lived user key that is committed to in an OpenID Connect
ID Token issued by the user's Identity Provider (IdP) and that
signs each of the user's device keys. The binding chain is
delivered to peers, who verify it and store the trusted user key
in their Personal Address Book (PAB). Peers may rely on the IdP
for the initial binding or verify the user key out of band; in
either case the MOCHA Provider and its relays are not trusted to
vouch for user keys.

--- middle

# Introduction

MOCHA Identity {{MOCHA-IDENTITY}} defines how users authenticate
to providers and obtain authorization tokens for relay access.
That is infrastructure-level trust: proving to relays that a
client is permitted to publish or subscribe.

This document addresses a different trust relationship:
peer-to-peer trust between users. When Alice wants to
communicate with Bob, she needs to verify that the keys used
to encrypt and sign messages actually belong to Bob, not to
an impersonator or a compromised intermediary.

MOCHA solves this with a binding chain:

1. Each device key is signed by the user's long-lived user key.
2. The user key is committed to in an OIDC ID Token {{OIDC}}
   issued by the user's IdP, and the user key signs an identity
   binding referencing that token.
3. The chain is published on a MOQT track and carried in MLS
   credentials, where peers verify it.
4. Verified user keys are stored in the peer's Personal Address
   Book (PAB) {{MOCHA-PAB}}.

Two trust models are supported, with different guarantees.
With IdP-based trust, a peer accepts the user key because the
IdP issued a token committing to it; an IdP compromise can
therefore impersonate users. With out-of-band verification, a
peer compares the user key fingerprint over a trusted channel,
and trust is independent of the IdP. Neither model trusts the
MOCHA Provider or its relays, which can only withhold or delay
binding chains, not forge them.

# Conventions and Definitions

{::boilerplate bcp14-tagged}

This document uses terminology defined in {{MOCHA-ARCH}},
including Provider, Organization, User, Device, and DevID.

The following additional terms are used:

User Key:
: A long-lived signature key pair owned by a user. The public
  half is the user's stable cryptographic identity. All device
  keys and identity assertions bind to this key.

Key-Holding Device:
: A device of the user that holds the private half of the user
  key and can therefore create bindings (see {{key-custody}}).

Device Key:
: A signature key pair generated by a single device. Bound
  to the user key via a device binding.

Binding Chain:
: The signed set of statements linking device keys to the user
  key and the user key to an OIDC ID Token, together with any
  revocation and rotation statements (see {{chain-format}}).

Fingerprint:
: A short hash of the user's public key suitable for
  out-of-band verification, computed as specified in
  {{fingerprint}}.

All timestamps in this document (`issued_at`, `revoked_at`,
`rotated_at`) are unsigned integers counting seconds since the
Unix epoch (1970-01-01T00:00:00Z), ignoring leap seconds.

~~~

               binding   |      |    |  binding
                         v      |    v
              +----------+--+   |  +-+------------+
              | Device Key  |   |  | Device Key   |

                                v
                      +---------+-----+
                      | Device Key    |
                      | (laptop)      |

~~~
{: #fig-hierarchy title="Key Hierarchy"}

A user has exactly one current user key at a time. A user may
have multiple devices, each with its own device key. All device
keys are signed by the current user key.

The ID Token commits to the user key (see {{oauth-binding}}),
so a verifier that trusts the IdP learns that the user
authenticated as the token's subject while holding that key.

## User Key Custody {#key-custody}

The private half of the user key is held by one or more of the
user's devices, called key-holding devices. Implementations
SHOULD store it in non-exportable, hardware-backed storage
(e.g., a secure enclave or TPM) where available. A device that
does not hold the user key holds only its own device key and
cannot create or revoke bindings.

Adding a new device requires a key-holding device to sign a
device binding for it. The new device's public key and DevID
MUST be conveyed to the key-holding device over an
authenticated channel (for example, a QR code displayed on one
device and scanned by the other). The pairing protocol is out
of scope for this document.

Implementations MAY synchronize the user key across devices
(for example, through a platform keychain). Every device that
receives the key is then a key-holding device, and compromise
of any of them is a compromise of the user key.

# Encoding and Signatures {#signing}

## Algorithms

Every public key in this document is accompanied by a signature
algorithm identifier, a `SignatureScheme` value from the TLS
SignatureScheme registry {{RFC8446}} (for example, `ed25519`,
0x0807). Implementations MUST support `ed25519`. A device key's
algorithm MUST match the signature scheme of the MLS
ciphersuite of every group in which it is used.

## Signed Content {#signed-content}

Signatures are computed over a binary encoding, not over JSON,
so that the same signature verifies in the JSON form
({{chain-format}}) and in the MLS credential form
({{mls-credential}}). Structures are encoded using the
presentation language of {{MLS}} Section 2.1, with
variable-length vectors prefixed by a variable-length integer
(`<V>`).

~~~
  struct {
    opaque label<V>;
    opaque content<V>;
  } MochaLabeledContent;
~~~

The `label` is the ASCII string "MOCHA 1.0 " followed by the
statement label given for each structure below. The `content`
is the encoding of that structure. A signature is computed by
the indicated key over the encoded MochaLabeledContent. The
distinct prefix prevents a MOCHA signature from being accepted
as an MLS signature, which uses the prefix "MLS 1.0 ", and
vice versa.

Labels and contents:

~~~
  /* label "DeviceBinding" */
  struct {
    uint16 sig_alg;            /* user key algorithm */
    opaque user_key<V>;
    uint16 device_sig_alg;     /* device key algorithm */
    opaque device_key<V>;
    opaque device_id<V>;
    uint64 issued_at;
  } DeviceBindingTBS;

  /* label "IdentityBinding" */
  struct {
    uint16 sig_alg;
    opaque user_key<V>;
    opaque oauth_issuer<V>;
    opaque oauth_subject<V>;
    opaque nonce_salt<V>;
    opaque id_token_hash[32];
    uint64 issued_at;
  } IdentityBindingTBS;

  /* label "DeviceRevocation" */
  struct {
    uint16 sig_alg;
    opaque user_key<V>;
    uint16 device_sig_alg;
    opaque device_key<V>;
    opaque device_id<V>;
    uint64 revoked_at;
  } DeviceRevocationTBS;

  /* label "KeyRotation" */
  struct {
    uint16 old_sig_alg;
    opaque old_key<V>;
    uint16 new_sig_alg;
    opaque new_key<V>;
    uint64 rotated_at;
  } KeyRotationTBS;

  /* label "BindingChain" */
  struct {
    uint16 sig_alg;
    opaque user_key<V>;
    uint64 seq;
    uint64 issued_at;
    opaque entry_hashes<V>;    /* concatenated 32-byte hashes */
  } BindingChainTBS;
~~~

Strings (issuer, subject, DevID) are encoded as their UTF-8
bytes. In the JSON forms below, binary values are encoded as
base64url without padding {{RFC4648}} and integers as JSON
numbers.

## Fingerprint {#fingerprint}

The fingerprint of a user key is the first 16 bytes (128 bits)
of SHA-256 computed over the MochaLabeledContent with label
"MOCHA 1.0 Fingerprint" and content:

~~~
  struct {
    uint16 sig_alg;
    opaque user_key<V>;
  } FingerprintInput;
~~~

When displayed, the fingerprint SHOULD be shown as 32
lowercase hexadecimal digits in eight groups of four, for
example `3f2a 91c0 77de 0b14 c5a8 e902 4d61 aa37`.

# Device Binding {#device-binding}

When a user adds a new device, the device generates a device
key pair and a key-holding device signs a device binding for
it with the user key:

~~~json
{
  "type": "device_binding",
  "sig_alg": 2055,
  "user_key": "<user public key>",
  "device_sig_alg": 2055,
  "device_key": "<device public key>",
  "device_id": "<DevID>",
  "issued_at": 1751000000,
  "signature": "<signature by user key over DeviceBindingTBS>"
}
~~~

The `device_id` MUST be unique among the user's device
bindings. A user MAY have multiple device bindings active
simultaneously (one per device). A device binding is withdrawn
by device revocation ({{device-revocation}}).

# Identity Binding {#oauth-binding}

## Committing the User Key in the ID Token {#key-commitment}

A signature by the user key over an ID Token alone does not
show that the IdP associated the token with that key: anyone
who obtains a copy of the token could sign it with a key of
their own. MOCHA therefore requires that the ID Token itself
commit to the user key through the OIDC `nonce` parameter.

To create an identity binding, a key-holding device:

1. Generates a random `nonce_salt` of at least 16 bytes.
2. Computes the commitment as SHA-256 over the
   MochaLabeledContent with label "MOCHA 1.0 UserKeyCommitment"
   and content:

   ~~~
     struct {
       uint16 sig_alg;
       opaque user_key<V>;
       opaque nonce_salt<V>;
     } UserKeyCommitment;
   ~~~

3. Performs an OIDC authentication request {{OIDC}} with
   `nonce` set to the base64url encoding (without padding) of
   the commitment, and `client_id` set to the Provider's
   key-binding client ID (see {{token-exposure}}).
4. Signs an identity binding over the resulting ID Token.

The salt prevents an observer from linking authentication
requests to a user key before the binding is published.

Because OIDC does not guarantee that ID Tokens obtained by
refresh carry the original `nonce`, a new identity binding
MUST be obtained through a fresh authentication request (which
MAY be non-interactive, e.g., using `prompt=none`).

## Identity Binding Statement

~~~json
{
  "type": "identity_binding",
  "sig_alg": 2055,
  "user_key": "<user public key>",
  "oauth_issuer": "https://idp.example.com",
  "oauth_subject": "248289761001",
  "nonce_salt": "<salt>",
  "id_token_hash": "<SHA-256 of the ID Token>",
  "issued_at": 1751000000,
  "signature": "<signature by user key over IdentityBindingTBS>"
}
~~~

The `oauth_issuer` and `oauth_subject` are the ID Token's `iss`
and `sub` claims. The OIDC `sub` is an opaque identifier
assigned by the IdP and is not an email address. The
`id_token_hash` is SHA-256 over the ASCII bytes of the ID Token
in JWS compact serialization.

## Binding Lifetime

ID Tokens are short-lived, but an identity binding is meant to
be verifiable after the token expires. The verifier therefore
checks that the binding was created while the token was valid
(see {{verification}}), rather than that the token is still
valid.

Verifiers MAY apply a local maximum age to identity bindings.
Users SHOULD refresh their identity binding at least every
7 days, and MUST refresh it when their `iss` or `sub` changes.

# Delivering the Binding Chain {#binding-delivery}

The binding chain is delivered to peers in two ways:

- In full, as a signed chain object on the user's keybinding
  track ({{delivery-mechanism}}). This is the only form that
  carries the ID Token and revocation and rotation statements.
- Partially, inside MLS credentials ({{mls-credential}}),
  which carry the identity binding and the one device binding
  for the LeafNode, but not the ID Token.

## Verification Architecture

~~~
  Alice                                              Bob
  +------------------+                       +------------------+
  |  Device A        |                       |  Device X        |
  |  (key-holding)   |                       |                  |
  +--------+---------+                       +--------+---------+
           |                                          |
           | (1) Publish signed chain                 |
           |     on keybinding track                  |
           v                                          |
  +--------+---------+         +----------+           |
  |  MoQ Relay       |-------->| MoQ Relay|---------->|
  +------------------+         +----------+           |
                                                      v
                                          (2) Subscribe to Alice's
                                              keybinding track
                                                      |
                                                      v
                                          (3) Verify:
                                              - ID Token valid and
                                                commits to user key?
                                              - chain, identity and
                                                device signatures?
                                                      |
                                                      v
                                          (4) Trust decision; store
                                              Alice's user key in PAB
                                          +---+------------------+
                                          |  PAB                 |
                                          |  "Alice" -> user_key |
                                          +----------------------+
~~~

## Delivery Mechanism {#delivery-mechanism}

The binding chain is published on a dedicated MOQT
{{MoQTransport}} track:

~~~
  Namespace: ("mocha_v1", <Provider>, <OrgID>, "keybinding",
              <UserID>)
  Track: "chain"
~~~

Only the user's key-holding devices publish on this track.
Each update is published as a single object starting a new
group, and each object contains the complete current chain;
subscribers need only the latest object. Subscribers SHOULD
subscribe starting from the latest object and SHOULD keep the
subscription open for every contact in their PAB, so that
revocations and rotations are learned promptly.

The Provider SHOULD restrict subscription to this track to
authenticated users permitted to communicate with the
publisher, since the chain contains the ID Token and its
claims (see {{privacy}}).

## Chain Format {#chain-format}

Each object on the track is a JSON document:

~~~json
{
  "type": "binding_chain",
  "sig_alg": 2055,
  "user_key": "<current user public key>",
  "seq": 42,
  "issued_at": 1751100000,
  "id_token": "<ID Token, JWS compact serialization>",
  "entries": [
    {
      "type": "identity_binding",
      "sig_alg": 2055,
      "user_key": "...",
      "oauth_issuer": "https://idp.example.com",
      "oauth_subject": "248289761001",
      "nonce_salt": "...",
      "id_token_hash": "...",
      "issued_at": 1751000000,
      "signature": "..."
    },
    {
      "type": "device_binding",
      "sig_alg": 2055,
      "user_key": "...",
      "device_sig_alg": 2055,
      "device_key": "...",
      "device_id": "device-1",
      "issued_at": 1751000000,
      "signature": "..."
    },
    {
      "type": "device_binding",
      "sig_alg": 2055,
      "user_key": "...",
      "device_sig_alg": 2055,
      "device_key": "...",
      "device_id": "device-2",
      "issued_at": 1751100000,
      "signature": "..."
    }
  ],
  "signature": "<signature by user key over BindingChainTBS>"
}
~~~

The `entries` array MUST contain exactly one identity binding,
whose `id_token_hash` matches `id_token`. It contains one
device binding for each currently authorized device, and MAY
contain device revocations ({{device-revocation}}) and at most
one key rotation statement ({{key-rotation}}).

The `entry_hashes` field of BindingChainTBS is the
concatenation, in `entries` order, of SHA-256 over each
entry's encoded MochaLabeledContent. The chain signature thus
covers the exact set of entries, so a relay cannot add, remove,
or reorder entries without detection.

The `seq` field MUST increase by at least one with each
published chain and continues across key rotations.

## Verification Steps {#verification}

The verifier MUST perform the following checks, and MUST treat
the chain as unverified if any check fails:

1. Verify the chain `signature` under `user_key` and
   `sig_alg`, recomputing `entry_hashes` from `entries`.
2. If the verifier has previously verified a chain for this
   user, check that `seq` is greater than or equal to the
   highest `seq` seen; a lower `seq` indicates a rollback.
3. Validate the ID Token signature against the IdP's JWKS
   {{RFC7519}}. If the signing key identified by the token's
   `kid` is no longer published, the verifier MAY use a
   previously cached copy of that key; otherwise the chain is
   unverified until the user publishes a refreshed identity
   binding.
4. Check that the ID Token's `iss` equals `oauth_issuer` and
   that the issuer is one the verifier accepts for MOCHA.
5. Check that the ID Token's `sub` equals `oauth_subject`.
6. Check that the ID Token's `aud` contains the key-binding
   client ID associated with that issuer ({{token-exposure}}).
   The verifier does not require `aud` to name itself.
7. Check that the identity binding's `issued_at` lies between
   the ID Token's `iat` and `exp`, allowing for clock skew of
   at most 5 minutes. The token is not required to be
   unexpired at verification time.
8. Recompute the commitment from `sig_alg`, `user_key`, and
   `nonce_salt` ({{key-commitment}}) and check that it equals
   the ID Token's `nonce` claim.
9. Check that SHA-256 over the ID Token equals
   `id_token_hash`, and verify the identity binding signature
   under `user_key`.
10. For each device binding, check that its `sig_alg` and
    `user_key` equal the chain's, that its `device_id` is
    unique within the chain, and verify its signature.
11. Verify each device revocation and key rotation statement
    as described in {{device-revocation}} and {{key-rotation}}.

If all checks pass, the verifier knows that the IdP
authenticated the user as (`iss`, `sub`) during a request that
committed to the user key, and that each listed device key is
authorized by that user key.

# Trust Decisions and the Personal Address Book {#trust-pab}

Once a peer has verified the binding chain, they make a local
trust decision about whether to accept this identity. The
result is stored in their Personal Address Book (PAB)
{{MOCHA-PAB}}.

A PAB entry associates a contact with the contact's verified
user key, IdP identity, and the trust model used. The `id` is
the contact identity as defined in {{MOCHA-PAB}}, such as the
email address from a verified `email` claim (one with
`email_verified` true). The `fn` is the display name chosen by
the PAB owner. The PAB entry is represented as a jCard
{{RFC7095}}:

~~~json
{
  "op": "add",
  "id": "alice@example.com",
  "timestamp": 1751000000,
  "card": ["vcard", [
    ["version", {}, "text", "4.0"],
    ["fn", {}, "text", "Alice Smith"],
    ["email", {}, "text", "alice@example.com"],
    ["key", {}, "uri", "mocha:userkey:0807:<base64url-user-key>"],
    ["x-mocha-oauth", {}, "text",
      ["https://idp.example.com", "248289761001"]],
    ["x-mocha-trust", {}, "text", "oauth"]
  ]]
}
~~~

The `key` value is a `mocha:userkey:` URI consisting of the
four lowercase hexadecimal digits of `sig_alg` followed by a
colon and the base64url-encoded user key. The `x-mocha-oauth`
property holds the `iss` and `sub` of the verified identity
binding. The `x-mocha-trust` property is "oauth" or
"fingerprint" ({{trust-models}}).

## Trust Flow

~~~
  +------------------+                          +----------------+
  |  Binding chain   |                          |  PAB Entry     |
  |  (keybinding     |                          |  (local store) |
  |   track)         |                          +--------+-------+
  +--------+---------+                                   ^
           |                                             |
           v                                             |
  +--------+------------------------------+              |
  |  Verify Binding Chain                 |              |
  |  1. Chain and entry signatures        |              |
  |  2. ID Token (JWKS, iss, sub, aud)    |              |
  |  3. nonce commits to user key         |              |
  +--------+------------------------------+              |
           |                                             |
           v                                             |
  +--------+------------------------------+   store      |
  |  Trust Decision                       +--------------+
  |  - trust the IdP ("oauth"), and/or    |   user key
  |  - compare fingerprint out of band    |
  |    ("fingerprint")                    |
  +---------------------------------------+
~~~
{: #fig-trust title="Trust Flow"}

## Trust Models {#trust-models}

The trust decision MAY rely on:

IdP-Based Trust ("oauth"):
: The verifier trusts the IdP's assertion that the user
  authenticated as (`iss`, `sub`) while committing to the user
  key. This is sufficient for most enterprise deployments where
  the IdP is trusted infrastructure, but a compromised IdP can
  impersonate any of its users.

Out-of-Band Fingerprint Verification ("fingerprint"):
: The verifier compares the user key fingerprint
  ({{fingerprint}}) via a trusted channel (in person, phone
  call, verified messaging). This provides trust independent
  of any IdP.

Both:
: The verifier uses IdP-based trust initially and later
  upgrades the PAB entry's `x-mocha-trust` to "fingerprint"
  after out-of-band verification.

## Ongoing Trust

Once the PAB entry exists, a device key is trusted if a valid
device binding for it under the stored user key is known, from
the latest verified chain or from an MLS credential
({{mls-credential}}), and that device key has not been revoked
in any verified chain. The full chain, including the ID Token,
need not be re-verified for each message. The PAB acts as a
local trust anchor.

A verifier that receives a newer chain for a stored user key
MUST verify it ({{verification}}) and MUST NOT accept a chain
whose `iss` or `sub` differ from those stored in the PAB entry
without a new trust decision.

If the user key changes, the peer follows {{key-rotation}}.

# Key Rotation {#key-rotation}

~~~
  Time ---->

  +-------------+    key_rotation     +-------------+
  | Old User Key|  (signed by both)   | New User Key|
  | (retired)   +-------------------->|  (current)  |
  +------+------+                     +------+------+
         |                                   |
    device_bindings                    device_bindings
    (under old key)                    (under new key)
         |                                   |
    +----+----+                         +----+----+
    | Dev A   |                         | Dev A   |

    | Dev C   |   new user key)         | Dev C   |

  Peer's PAB:
    "Alice" -> old_key                "Alice" -> new_key
               (updated after verifying rotation and new chain)
~~~

## Planned Rotation

When a user rotates their user key while still holding the old
key, a key-holding device produces:

1. A new identity binding under the new key, from a fresh ID
   Token whose `nonce` commits to the new key
   ({{key-commitment}}).
2. New device bindings for all active devices under the new
   key.
3. A key rotation statement:

~~~json
{
  "type": "key_rotation",
  "old_sig_alg": 2055,
  "old_key": "<old user public key>",
  "new_sig_alg": 2055,
  "new_key": "<new user public key>",
  "rotated_at": 1752000000,
  "signature_old": "<signature by old key over KeyRotationTBS>",
  "signature_new": "<signature by new key over KeyRotationTBS>"
}
~~~

These are published as a new chain, signed by the new key,
whose `entries` include the rotation statement and whose `seq`
continues from the previous chain.

A peer with the old key in their PAB:

1. Verifies both rotation signatures, and that `old_key` is the
   key in their PAB and `new_key` is the chain's `user_key`.
2. Verifies the new chain fully ({{verification}}), including
   that `iss` and `sub` match the PAB entry.
3. Updates the PAB entry's `key` to the new key. The peer MAY
   carry over the existing `x-mocha-trust` level and SHOULD
   notify the user that the key changed.

Because step 2 requires a fresh ID Token committing to the new
key, an attacker who has stolen the old user key cannot rotate
the user to a key of their choosing without also
authenticating at the IdP as the user.

If a peer observes two different rotation statements from the
same old key, or a rotation whose new chain fails verification,
it MUST NOT update the PAB entry, MUST treat the contact as
unverified, and SHOULD alert the user. This situation indicates
that the old key is compromised.

## Lost or Compromised User Key

If the old key is unavailable (for example, every key-holding
device was lost), no rotation statement can be produced. The
user generates a new key and publishes a new chain. If the old
key is known to be compromised, the user SHOULD rotate when
possible, since a valid rotation lets peers detect a competing
rotation by an attacker.

A peer that receives a chain with a different user key for the
same (`iss`, `sub`) and no valid rotation from the stored key
MUST NOT replace the PAB entry automatically. Such a chain is
indistinguishable from impersonation by a compromised IdP. The
peer MUST make a new trust decision ({{trust-models}}) and
SHOULD alert the user, recommending fingerprint verification
when the previous entry was "fingerprint".

# Device Revocation {#device-revocation}

A user revokes a device key by having a key-holding device
publish a revocation statement signed by the current user key:

~~~json
{
  "type": "device_revocation",
  "sig_alg": 2055,
  "user_key": "<current user public key>",
  "device_sig_alg": 2055,
  "device_key": "<revoked device public key>",
  "device_id": "<DevID>",
  "revoked_at": 1751500000,
  "signature": "<signature by user key over DeviceRevocationTBS>"
}
~~~

The revocation is included in the `entries` of the next
published chain, and the corresponding device binding is
removed from it. Revocations SHOULD remain in the chain for a
deployment-defined period, RECOMMENDED to be at least 90 days,
so that peers who hold the device binding only from an MLS
credential learn of the revocation.

A device key that is not listed in a device binding in the
latest verified chain is no longer authorized, whether or not
an explicit revocation is present.

When a peer processes a revocation or the removal of a device
binding:

- It MUST reject messages signed by that device key that it
  receives afterwards. Because `revoked_at` and message
  timestamps can be chosen by an attacker holding the revoked
  device, they MUST NOT be used to accept such messages.
- It MAY retain messages from that device that it had already
  accepted, and SHOULD mark messages whose claimed timestamp is
  later than `revoked_at`.
- In MLS groups, it SHOULD cause the revoked device's leaves to
  be removed, as described in {{MOCHA-MLS-KEYING}}.

# MLS Credential Type {#mls-credential}

## Overview

MLS {{MLS}} requires each member to present a Credential in
their LeafNode that binds their identity to their MLS signature
key. MOCHA defines a custom MLS credential type that embeds
the identity binding and device binding directly, so that
members already in each other's PAB can validate credentials
without network access.

~~~
  MLS LeafNode
  +-------------------------------------------------------+
  |  signature_key: <device public key>                   |
  |                                                       |
  |  credential (type: mocha_binding_chain)               |
  |  +---------------------------------------------------+|
  |  |  identity_binding:                                ||
  |  |    user_key, oauth_issuer, oauth_subject,         ||
  |  |    nonce_salt, id_token_hash, sig                 ||
  |  |                                                   ||
  |  |  device_binding:                                  ||
  |  |    user_key, device_key, device_id, sig           ||
  |  |                                                   ||
  |  |  (device_key == LeafNode.signature_key)           ||
  |  +---------------------------------------------------+|
  +-------------------------------------------------------+
~~~
{: #fig-leafnode title="mocha_binding_chain Credential in a LeafNode"}

The credential lets a group member verify the chain from the
MLS signature key to the user key and check the user key
against their local PAB. It does not carry the ID Token or
revocation state; those are obtained from the keybinding track
({{delivery-mechanism}}).

This document is normative for the mocha_binding_chain
credential and its validation. {{MOCHA-MLS-KEYING}} profiles
its use in MOCHA MLS groups and defines a related credential
for virtual clients.

## Credential Structure

The MOCHA binding chain credential uses the following MLS
credential type:

~~~
  credential_type = mocha_binding_chain (TBD1)
~~~

The credential body is encoded as:

~~~
  struct {
    IdentityBinding identity_binding;
    DeviceBinding device_binding;
  } MochaBindingChainCredential;

  struct {
    uint16 sig_alg;
    opaque user_key<V>;
    opaque oauth_issuer<V>;
    opaque oauth_subject<V>;
    opaque nonce_salt<V>;
    opaque id_token_hash[32];
    uint64 issued_at;
    opaque signature<V>;
  } IdentityBinding;

  struct {
    uint16 sig_alg;
    opaque user_key<V>;
    uint16 device_sig_alg;
    opaque device_key<V>;
    opaque device_id<V>;
    uint64 issued_at;
    opaque signature<V>;
  } DeviceBinding;
~~~

The fields other than `signature` are the corresponding TBS
structures of {{signed-content}}, and each `signature` is the
same signature carried in the JSON form.

The `device_key` in the DeviceBinding MUST be identical to the
`signature_key` in the LeafNode, and `device_sig_alg` MUST be
the signature scheme of the group's ciphersuite. This binds
the MLS signature key to the identity chain.

## Credential Validation {#credential-validation}

When a group member receives a LeafNode with a
mocha_binding_chain credential (in a Commit, Welcome, or
KeyPackage), validation proceeds as:

~~~
  Received MLS LeafNode
         |
         v
  (1) Assert: device_key == LeafNode.signature_key
      Assert: device_sig_alg matches ciphersuite
         |
         v
  (2) Assert: same sig_alg and user_key in
      IdentityBinding and DeviceBinding
         |
         v
  (3) Verify DeviceBinding.signature and
      IdentityBinding.signature under user_key
         |
         v
  (4) Look up user_key in local PAB
         |
         +-------> [FOUND] --> check iss/sub match the entry
         |                     and device_key not revoked
         |                     --> trusted, use PAB display name
         |
         +-------> [NOT FOUND] --> unverified; fetch chain
                   from keybinding track when possible,
                   verify it, apply trust decision
~~~
{: #fig-cred-validate title="Credential Validation"}

If steps 1 through 3 fail, the credential is invalid and the
LeafNode MUST be rejected as specified in {{MLS}}.

If the user key is found in the PAB, the member checks that
`oauth_issuer` and `oauth_subject` match the PAB entry and
that the device key has not been revoked in the latest verified
chain ({{device-revocation}}). If these checks pass, the member
is trusted and displayed using the PAB entry's name.

If the user key is not in the PAB, the member is unverified.
The client fetches and verifies the full chain
({{verification}}) when connectivity permits and applies a
trust decision ({{trust-models}}). Until a decision is made,
the client MUST NOT present the member as verified. Local
policy determines whether group operations involving
unverified members proceed. Because MLS processing is often
automatic, clients SHOULD NOT block it on an interactive
prompt.

## Offline Operation

This credential type enables offline MLS credential validation:

- The credential is self-contained in the LeafNode; no
  network call to a Provider or Token Service is needed.

- The PAB lookup is local and works without connectivity.

- Existing group members who already have each other's user
  keys in their PABs can verify credentials entirely offline.
  Revocation state is as current as the latest chain each
  member has seen.

- New members (not yet in PAB) require either the full chain
  from the keybinding track, verified against the IdP's JWKS
  (which can be cached), or out-of-band fingerprint
  verification.

This contrasts with Provider-signed credentials, which require
the Provider to be reachable for issuance and which concentrate
trust in the Provider. The binding chain credential
distributes trust to the endpoints.

## Relationship to Other Credential Types

Deployments MAY support other credential types alongside
mocha_binding_chain:

- mocha_binding_chain: Self-certified by the user key, offline
  validation, trust anchored in the PAB. Used for peer-to-peer
  trust.

- x509 (MLS built-in type): A certificate issued by a
  Provider or enterprise CA. Requires the CA to be reachable
  for issuance. Used when enterprise policy mandates a
  centralized credential authority.

The MLS `basic` credential carries an identity with no proof
of possession or issuer signature and SHOULD NOT be used in
MOCHA deployments.

When multiple credential types are in use in a group, each
LeafNode is validated according to its own credential type.
As required by {{MLS}}, every credential type in use in the
group MUST be listed in each member's `capabilities`. Groups
MAY use the `required_capabilities` extension to require
support for mocha_binding_chain.

# Security Considerations

## User Key Compromise

The user key is the root of trust for peer-to-peer identity.
An attacker holding it can sign device bindings for arbitrary
device keys and impersonate the user, including in MLS
credentials, which do not require access to the keybinding
track. Implementations SHOULD keep the user key in
non-exportable, hardware-backed storage and SHOULD minimize the
number of key-holding devices ({{key-custody}}). Rotating the
user key requires a fresh IdP authentication
({{key-rotation}}), so a stolen user key alone does not allow
the attacker to take over the user's identity at peers.

## IdP Trust

IdP-based trust is only as strong as the IdP. A compromised
IdP can issue ID Tokens committing to an attacker's user key,
and peers relying on IdP-based trust will accept them for new
contacts. Peers that already hold the user's key detect a new
key without a valid rotation ({{key-rotation}}). Out-of-band
fingerprint verification provides trust independent of the IdP
and SHOULD be used for high-assurance contacts.

## ID Token Exposure and Replay {#token-exposure}

The binding chain publishes the user's ID Token. If a service
accepted that token as a bearer credential, anyone who can read
the keybinding track could replay it. To prevent this:

- Each Provider MUST register a key-binding client ID at the
  IdP, distinct from any client ID whose ID Tokens are accepted
  for authentication. ID Tokens used in identity bindings MUST
  be requested with the key-binding client ID.
- The Token Service of {{MOCHA-IDENTITY}} and any other relying
  party MUST NOT accept ID Tokens whose `aud` is the key-binding
  client ID as authentication.

Verifiers learn the key-binding client ID for each accepted
issuer by means outside the scope of this document.

## Freshness and Rollback

Relays see binding chain traffic but cannot forge signatures:
the chain contains only public keys, signatures, and the ID
Token, and no private key material is transmitted. A relay can,
however, withhold updates or replay an older chain to hide a
revocation or rotation. The chain `seq` lets verifiers reject
older chains than one already seen, but cannot reveal an update
the verifier never received. Verifiers SHOULD keep their
subscriptions to contacts' keybinding tracks open and MAY treat
contacts whose chain has not been refreshed within a local
maximum age as unverified.

## Privacy {#privacy}

The ID Token typically contains personal data such as name and
email address, and the chain reveals the number of the user's
devices and their DevIDs. Providers SHOULD limit subscription
to the keybinding track ({{delivery-mechanism}}), and users
SHOULD request only the claims needed for key binding when
authenticating with the key-binding client ID.
